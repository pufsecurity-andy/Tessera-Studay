Tessera Code Map：TesseraHSM 六個 repo 的結構

Tessera 是 Microsoft 主導、Marvell 和 Oracle 共同署名的開源 HSM 專案，透過 OCP 推動。晶片需求規格（CRD）開宗明義把 Tessera 定義為「在 OCP 公開開發的下一代 Azure Integrated HSM」。它延續 Caliptra 的路線：規格、晶片 RTL、韌體、主機 SDK 全部公開，目標是讓每台伺服器、每個 TEE、每台 VM 旁邊都有一顆 FIPS 140-3 Level 3 的 HSM，金鑰不必離開 HSM 邊界也能跨廠商、跨雲移動。

05信任鏈與金鑰階層

Tessera 用三條憑證鏈夾出一個分區：製造商鏈證明「這是真的 Tessera」，Tessera Owner 鏈證明「這顆屬於哪個服務或企業」，Partition Owner 鏈證明「這個分區屬於誰」。三條鏈必須全部驗證通過。

金鑰家族

金鑰來源與用途
BKS1 Manufacturer / Root Seed由製造商或 root owner 控制，同一類裝置共用（程式碼中依韌體 SVN 分列）
BKS2 Tessera Owner Seed以 AOAC 背書的 sealing key 安裝；備份只能還原到同一 Owner 的裝置
BKS3 Partition Owner Seed由 TEE 或 Sealing Service 用 POTA 背書的 HPKE 金鑰送進分區；同一 Security Domain 共用
BK（Backup Key）由 BKS1、BKS2、BKS3 加上 owner 信任錨金鑰經 KDF 推導；用來遮罩 Masking Key，產生 BMK（備份用的 MK）
MK / SDMK分區初始化時隨機產生的 Masking Key（或 Security Domain 共用的 SDMK），所有 masked key blob 都在它底下；可透過分區複製傳給同一 POTA 的分區
Session sealing keyAES-256-GCM，由 DRBG＋VM nonce＋裝置身分推導；VM 斷線或 session 關閉就清除
TMK（DARC）一次性 AES-256 金鑰，跨廠商搬一把 key 時，用 HPKE-Auth（P-384）封裝

三種「搬金鑰」的協定

  • Masking Key Transfer：在同一個 POTA 底下複製分區 MK，等於擴大 Security Domain。用於 HA 和水平擴展。
  • DARC：跨廠商只搬一把金鑰，不擴大 domain。目前只支援 EC 私鑰，PQC/hybrid 的 HPKE profile 還是 Open Item。
  • SKR / Key Import：相容舊流程，需要 CKA_EXTRACTABLE。規格把 Key Export 列為反模式，保留 SKR 只是為了向後相容。

Command Specification — Security Considerations

tessera-specs/Tessera - Command Specification.md:692

The following security considerations apply to implementations of this protocol.

FIPS_APPROVED Flag

The FIPS_APPROVED flag in the response header (bit 0 of the Flags byte) indicates whether the device used FIPS 140-2/140-3 approved cryptographic algorithms to process the request. This flag is informational only. Host software that requires FIPS compliance MUST independently verify the device's FIPS certification status through out-of-band means (e.g., hardware attestation, certificate chain validation) and MUST NOT rely solely on this flag for compliance decisions.

Sealed Key Handling

The sealed_key TOC entry type carries opaque, device-sealed key material. Intermediaries and host software MUST treat sealed key blobs as opaque byte sequences and MUST NOT attempt to parse, modify, or interpret their contents. Sealed keys SHOULD be stored in secure, access-controlled memory when held by the host.

Input Validation

Implementations MUST perform thorough bounds-checking on all incoming messages:

  • Verify that Offset + Length for every Offset/Length TOC entry falls within the actual variable-length data section.
  • Verify that the total message size is consistent with the TOC Count and the referenced data regions.
  • Reject messages that fail validation with status code 0x00000003 (Malformed Request) and do not process them further.

Failure to validate inputs can lead to buffer over-reads or other memory safety vulnerabilities, which are especially critical in device driver contexts.

Transport Security

This protocol does not define encryption or authentication at the wire level. If the transport channel is not physically secured (e.g., communication over a shared bus), implementations SHOULD layer appropriate transport security (encryption, message authentication) beneath this protocol.

Command Specification — Default-PSK gate

tessera-specs/Tessera - Command Specification.md:940

Partitions ship with publicly-known compiled-in default PSKs (TESSERAHSM-DEFAULT-CO-PSK-v1---- / TESSERAHSM-DEFAULT-CU-PSK-v1----) so they are usable at bring-up. A session opened against an un-rotated default PSK has no authentication value and the dispatcher refuses to run any production work on it.

While the calling session's role still has its default PSK, the only in-session commands permitted are:

OpcodeCommandWhy it's allowed
0x05SessionCloseTear-down has no security impact
0x06PskChangeThe rotation itself

Any other in-session opcode returns DefaultPskMustRotate (0x087000E6). The gate is per role: rotating the CO PSK unlocks CO sessions but does not affect CU; rotating the CU PSK is a separate operation. Out-of-session opcodes (ApiRev, SessionOpenInit, SessionOpenFinish, PartInfo, GetCertChainInfo, GetCertificate) are never gated so a client can always open the bootstrap session.

Bootstrap sequence (mandatory on first provisioning):

  • Open a session for the role under the default PSK.
  • Issue PskChange as the first in-session command.
  • (Optional) SessionClose; subsequent sessions are unrestricted.

The gate is safe-by-default in code: future opcodes added to the dispatcher are gated unless explicitly placed on the allowed_with_default_psk allow-list in fw/core/lib/src/ddi/tbor/mod.rs.

DARC Specification — Replay and Mutual-Authentication Guarantees

tessera-specs/Tessera - DARC Specification.md:391

The HPKE-Auth seal binds the transfer to both endpoints' KEX identities; an attacker cannot substitute a receiver (it lacks RcvrPriv) or forge the sender (it lacks the POTA-endorsed sender key). Certificate-chain validation against the policy-pinned DATA/POTA anchors prevents a mis-owned or unauthenticated device from participating. Because the TMK and KEX keys are fresh per campaign, a captured sealed_tmk or wrapped_key cannot be replayed into a different campaign.

DARC Specification — Masked-Key Handling and Zeroization

tessera-specs/Tessera - DARC Specification.md:358

Every DARC handler recovers secrets into transient buffers and zeroizes them on every exit path, including error paths: KEX private keys, the TMK, the big-endian private scalar d, and the COSE_Key plaintext. Masked blobs decrypted in place during unmasking are scrubbed after use. Only non-secret values (public keys, kid labels) survive a handler. Secret scrubbing uses a volatile wipe so the store cannot be elided by the optimizer.

Chip Requirements — Physical Security

tessera-specs/Tessera - Chip Requirements Specification.md:419

Tessera SHALL be certified to FIPS 140-3 level 3 at the full chip boundary.

Tessera’s cryptographic acceleration blocks, memories, and buffers storing keys in plain text SHALL have the following tamper defense mechanisms:

  • Tamper Shield
  • Temperature Sensor
  • Multi Register and Multi bit Registers with parity protection on memory protection configuration.
  • Security sensitive registers shall be multi-bit. Example: a single bit should not represent debug enabled.
  • Frequency and Voltage monitors

完整的安全與信任需求（PCIe IDE/TDISP、Root of Trust、Firmware Security、Chassis Intrusion）請見 ASIC 分析頁的需求清單，章節選「安全與信任」。

tessera-sw — ddi_sock_server 檔頭註解

tessera-sw/examples/sock/ddi_sock_server/src/main.rs:1

Linux VSOCK server backed by an in-process HSM emulator. Run cargo run -p ddi_sock_server in a VSOCK-capable Linux guest. The server listens on port 1234 and uses partition 10. Clients connect to vsock://CID:1234, where CID is this guest's VSOCK context ID. This unauthenticated test transport is for trusted, isolated environments; it is not a production service. Emulator state is lost when the server exits. Requests with OOB pointers or lengths are rejected: this wire format cannot transfer descriptor arrays or the buffers they reference.

tessera-sw — PskChange 的 Replay model

tessera-sw/fw/core/lib/src/ddi/tbor/psk_change.rs:12

Cross-session replay is structurally impossible: param_key is HPKE-derived per session, so an envelope captured from session A cannot decrypt under session B's key (the AEAD tag fails before any plaintext is produced).

Intra-session replay is bounded to one successful change per session: the handler marks the session as "change used" on success; a second PskChange on the same session is rejected with InvalidPermissions.
