Tessera Code Map：TesseraHSM 六個 repo 的結構

Tessera 是 Microsoft 主導、Marvell 和 Oracle 共同署名的開源 HSM 專案，透過 OCP 推動。晶片需求規格（CRD）開宗明義把 Tessera 定義為「在 OCP 公開開發的下一代 Azure Integrated HSM」。它延續 Caliptra 的路線：規格、晶片 RTL、韌體、主機 SDK 全部公開，目標是讓每台伺服器、每個 TEE、每台 VM 旁邊都有一顆 FIPS 140-3 Level 3 的 HSM，金鑰不必離開 HSM 邊界也能跨廠商、跨雲移動。

05信任鏈與金鑰階層

Tessera 用三條憑證鏈夾出一個分區：製造商鏈證明「這是真的 Tessera」，Tessera Owner 鏈證明「這顆屬於哪個服務或企業」，Partition Owner 鏈證明「這個分區屬於誰」。三條鏈必須全部驗證通過。

金鑰家族

金鑰來源與用途
BKS1 Manufacturer / Root Seed由製造商或 root owner 控制，同一類裝置共用（程式碼中依韌體 SVN 分列）
BKS2 Tessera Owner Seed以 AOAC 背書的 sealing key 安裝；備份只能還原到同一 Owner 的裝置
BKS3 Partition Owner Seed由 TEE 或 Sealing Service 用 POTA 背書的 HPKE 金鑰送進分區；同一 Security Domain 共用
BK（Backup Key）由 BKS1、BKS2、BKS3 加上 owner 信任錨金鑰經 KDF 推導；用來遮罩 Masking Key，產生 BMK（備份用的 MK）
MK / SDMK分區初始化時隨機產生的 Masking Key（或 Security Domain 共用的 SDMK），所有 masked key blob 都在它底下；可透過分區複製傳給同一 POTA 的分區
Session sealing keyAES-256-GCM，由 DRBG＋VM nonce＋裝置身分推導；VM 斷線或 session 關閉就清除
TMK（DARC）一次性 AES-256 金鑰，跨廠商搬一把 key 時，用 HPKE-Auth（P-384）封裝

三種「搬金鑰」的協定

  • Masking Key Transfer：在同一個 POTA 底下複製分區 MK，等於擴大 Security Domain。用於 HA 和水平擴展。
  • DARC：跨廠商只搬一把金鑰，不擴大 domain。目前只支援 EC 私鑰，PQC/hybrid 的 HPKE profile 還是 Open Item。
  • SKR / Key Import：相容舊流程，需要 CKA_EXTRACTABLE。規格把 Key Export 列為反模式，保留 SKR 只是為了向後相容。

Command Specification — 安全考量Command Specification — Security Considerations

tessera-specs/Tessera - Command Specification.md:692

以下安全考量適用於此協定的實作。

原文The following security considerations apply to implementations of this protocol.

FIPS_APPROVED 旗標FIPS_APPROVED Flag

回應標頭中的 FIPS_APPROVED 旗標（Flags 位元組的 bit 0）表示裝置處理此請求時是否使用了 FIPS 140-2/140-3 核准的密碼演算法。此旗標僅供參考。需要符合 FIPS 的主機軟體必須透過頻外方式（例如硬體證明、憑證鏈驗證）獨立確認裝置的 FIPS 認證狀態，且不得只依賴此旗標做合規判斷。

原文The FIPS_APPROVED flag in the response header (bit 0 of the Flags byte) indicates whether the device used FIPS 140-2/140-3 approved cryptographic algorithms to process the request. This flag is informational only. Host software that requires FIPS compliance MUST independently verify the device's FIPS certification status through out-of-band means (e.g., hardware attestation, certificate chain validation) and MUST NOT rely solely on this flag for compliance decisions.

Sealed Key 處理Sealed Key Handling

sealed_key 這種 TOC entry 承載不透明、由裝置封裝的金鑰材料。中介者與主機軟體必須把 sealed key blob 視為不透明的位元組序列，不得嘗試解析、修改或解讀其內容。主機持有 sealed key 時，應該存放在安全、有存取控制的記憶體中。

原文The sealed_key TOC entry type carries opaque, device-sealed key material. Intermediaries and host software MUST treat sealed key blobs as opaque byte sequences and MUST NOT attempt to parse, modify, or interpret their contents. Sealed keys SHOULD be stored in secure, access-controlled memory when held by the host.

輸入驗證Input Validation

實作必須對所有收到的訊息做完整的邊界檢查：

原文Implementations MUST perform thorough bounds-checking on all incoming messages:
  • 確認每個 Offset/Length TOC entry 的 Offset + Length 都落在實際的變長資料區內。
    原文Verify that Offset + Length for every Offset/Length TOC entry falls within the actual variable-length data section.
  • 確認訊息總大小與 TOC 數量及所參照的資料區一致。
    原文Verify that the total message size is consistent with the TOC Count and the referenced data regions.
  • 以狀態碼 0x00000003（Malformed Request）拒絕驗證失敗的訊息，且不再進一步處理。
    原文Reject messages that fail validation with status code 0x00000003 (Malformed Request) and do not process them further.

未驗證輸入可能導致緩衝區越界讀取或其他記憶體安全漏洞，在裝置驅動程式中尤其嚴重。

原文Failure to validate inputs can lead to buffer over-reads or other memory safety vulnerabilities, which are especially critical in device driver contexts.

傳輸安全Transport Security

此協定沒有在線路層定義加密或認證。如果傳輸通道沒有實體保護（例如經由共用匯流排通訊），實作應該在此協定之下加上適當的傳輸安全（加密、訊息認證）。

原文This protocol does not define encryption or authentication at the wire level. If the transport channel is not physically secured (e.g., communication over a shared bus), implementations SHOULD layer appropriate transport security (encryption, message authentication) beneath this protocol.

Command Specification — 預設 PSK 限制Command Specification — Default-PSK gate

tessera-specs/Tessera - Command Specification.md:940

分區出貨時帶有公開已知、編譯在程式中的預設 PSK（TESSERAHSM-DEFAULT-CO-PSK-v1---- / TESSERAHSM-DEFAULT-CU-PSK-v1----），以便在 bring-up 時可以使用。以尚未輪替的預設 PSK 開啟的 session 沒有認證價值，分派器會拒絕在上面執行任何正式工作。

原文Partitions ship with publicly-known compiled-in default PSKs (TESSERAHSM-DEFAULT-CO-PSK-v1---- / TESSERAHSM-DEFAULT-CU-PSK-v1----) so they are usable at bring-up. A session opened against an un-rotated default PSK has no authentication value and the dispatcher refuses to run any production work on it.

當呼叫 session 的角色仍使用預設 PSK 時，只允許下列 in-session 指令：

原文While the calling session's role still has its default PSK, the only in-session commands permitted are:

0x05SessionClose關閉 session 不影響安全Tear-down has no security impact
0x06PskChange輪替本身The rotation itself

其他任何 in-session opcode 都會回傳 DefaultPskMustRotate（0x087000E6）。此限制以角色為單位：輪替 CO PSK 會解鎖 CO session，但不影響 CU；輪替 CU PSK 是另一個獨立的操作。Out-of-session 的 opcode（ApiRev、SessionOpenInit、SessionOpenFinish、PartInfo、GetCertChainInfo、GetCertificate）永遠不受限制，所以 client 一定能開啟 bootstrap session。

原文Any other in-session opcode returns DefaultPskMustRotate (0x087000E6). The gate is per role: rotating the CO PSK unlocks CO sessions but does not affect CU; rotating the CU PSK is a separate operation. Out-of-session opcodes (ApiRev, SessionOpenInit, SessionOpenFinish, PartInfo, GetCertChainInfo, GetCertificate) are never gated so a client can always open the bootstrap session.

  • 以預設 PSK 為該角色開啟一個 session。
    原文Open a session for the role under the default PSK.
  • 送出 PskChange 作為第一個 in-session 指令。

原文The gate is safe-by-default in code: future opcodes added to the dispatcher are gated unless explicitly placed on the allowed_with_default_psk allow-list in fw/core/lib/src/ddi/tbor/mod.rs.

DARC Specification — 重放與雙向認證保證DARC Specification — Replay and Mutual-Authentication Guarantees

tessera-specs/Tessera - DARC Specification.md:391

HPKE-Auth 封裝把這次傳輸綁定到兩端的 KEX 身分；攻擊者無法替換接收者（它沒有 RcvrPriv），也無法偽造發送者（它沒有經 POTA 背書的發送者金鑰）。以政策固定的 DATA/POTA 信任錨驗證憑證鏈，可以防止擁有者不符或未經認證的裝置參與。由於 TMK 與 KEX 金鑰在每次 campaign 都是新的，截獲的 sealed_tmk 或 wrapped_key 無法被重放到另一個 campaign。

原文The HPKE-Auth seal binds the transfer to both endpoints' KEX identities; an attacker cannot substitute a receiver (it lacks RcvrPriv) or forge the sender (it lacks the POTA-endorsed sender key). Certificate-chain validation against the policy-pinned DATA/POTA anchors prevents a mis-owned or unauthenticated device from participating. Because the TMK and KEX keys are fresh per campaign, a captured sealed_tmk or wrapped_key cannot be replayed into a different campaign.

DARC Specification — Masked Key 處理與清除DARC Specification — Masked-Key Handling and Zeroization

tessera-specs/Tessera - DARC Specification.md:358

每個 DARC handler 都把秘密還原到暫時緩衝區，並在每一條結束路徑（包括錯誤路徑）上清除：KEX 私鑰、TMK、big-endian 私密純量 d，以及 COSE_Key 明文。解遮罩時原地解密的 masked blob 用完後會被清除。只有非秘密的值（公鑰、kid 標籤）會留在 handler 之外。秘密清除使用 volatile wipe，讓最佳化器無法省略這些寫入。

原文Every DARC handler recovers secrets into transient buffers and zeroizes them on every exit path, including error paths: KEX private keys, the TMK, the big-endian private scalar d, and the COSE_Key plaintext. Masked blobs decrypted in place during unmasking are scrubbed after use. Only non-secret values (public keys, kid labels) survive a handler. Secret scrubbing uses a volatile wipe so the store cannot be elided by the optimizer.

tessera-sw — PskChange 的 Replay model

tessera-sw/fw/core/lib/src/ddi/tbor/psk_change.rs:12

跨 session 重放在結構上不可能：param_key 是每個 session 以 HPKE 推導的，所以從 session A 截獲的 envelope 無法用 session B 的金鑰解密（AEAD tag 會在產生任何明文之前驗證失敗）。

原文Cross-session replay is structurally impossible: param_key is HPKE-derived per session, so an envelope captured from session A cannot decrypt under session B's key (the AEAD tag fails before any plaintext is produced).

同一 session 內的重放限制為每個 session 只能成功變更一次：成功後 handler 會把 session 標記為「已使用變更」；同一 session 上的第二次 PskChange 會以 InvalidPermissions 拒絕。

原文Intra-session replay is bounded to one successful change per session: the handler marks the session as "change used" on success; a second PskChange on the same session is rejected with InvalidPermissions.
