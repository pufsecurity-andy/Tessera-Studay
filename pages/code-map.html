Tessera：把 Azure Integrated HSM 開源成一個「伺服器內建 HSM」的產業標準

Tessera 是 Microsoft 主導、Marvell 和 Oracle 共同署名的開源 HSM 專案，透過 OCP 推動。晶片需求規格（CRD）開宗明義把 Tessera 定義為「在 OCP 公開開發的下一代 Azure Integrated HSM」。它延續 Caliptra 的路線：規格、晶片 RTL、韌體、主機 SDK 全部公開，目標是讓每台伺服器、每個 TEE、每台 VM 旁邊都有一顆 FIPS 140-3 Level 3 的 HSM，金鑰不必離開 HSM 邊界也能跨廠商、跨雲移動。

一句話結論：目前軟體已經相當成熟，晶片還是半成品。韌體、SDK、模擬器、OpenSSL 整合都能跑；RTL 只有密碼加速器，而且 12 個 IP 裡有 11 個是直接從 Caliptra 搬過來改名的。CRD 裡真正難做的部分還沒公開：key mover、pool manager、PCIe Gen6 IDE/TDISP 前端、GSRAM key vault、防竄改。這代表兩件事：一是商業上的進場窗口還開著；二是現在能拿去做安全宣稱的東西，大部分還停在模擬器。

05信任鏈與金鑰階層

Tessera 用三條憑證鏈夾出一個分區：製造商鏈證明「這是真的 Tessera」，Tessera Owner 鏈證明「這顆屬於哪個服務或企業」，Partition Owner 鏈證明「這個分區屬於誰」。三條鏈必須全部驗證通過。

金鑰家族

金鑰來源與用途
BKS1 Manufacturer / Root Seed由製造商或 root owner 控制，同一類裝置共用（程式碼中依韌體 SVN 分列）
BKS2 Tessera Owner Seed以 AOAC 背書的 sealing key 安裝；備份只能還原到同一 Owner 的裝置
BKS3 Partition Owner Seed由 TEE 或 Sealing Service 用 POTA 背書的 HPKE 金鑰送進分區；同一 Security Domain 共用
BK（Backup Key）由 BKS1、BKS2、BKS3 加上 owner 信任錨金鑰經 KDF 推導；用來遮罩 Masking Key，產生 BMK（備份用的 MK）
MK / SDMK分區初始化時隨機產生的 Masking Key（或 Security Domain 共用的 SDMK），所有 masked key blob 都在它底下；可透過分區複製傳給同一 POTA 的分區
Session sealing keyAES-256-GCM，由 DRBG＋VM nonce＋裝置身分推導；VM 斷線或 session 關閉就清除
TMK（DARC）一次性 AES-256 金鑰，跨廠商搬一把 key 時，用 HPKE-Auth（P-384）封裝

三種「搬金鑰」的協定

  • Masking Key Transfer：在同一個 POTA 底下複製分區 MK，等於擴大 Security Domain。用於 HA 和水平擴展。
  • DARC：跨廠商只搬一把金鑰，不擴大 domain。目前只支援 EC 私鑰，PQC/hybrid 的 HPKE profile 還是 Open Item。
  • SKR / Key Import：相容舊流程，需要 CKA_EXTRACTABLE。規格把 Key Export 列為反模式，保留 SKR 只是為了向後相容。
商業意義：DARC 是整套規格裡最有「標準價值」的部分。如果 Thales、Entrust、Utimaco 或各家雲端 HSM 都實作 DARC，企業就能向監管單位（DORA、OSFI、PCI-HSM）證明「隨時可以退出某家雲」，而且金鑰全程留在 HSM 邊界內。

06資安專家審查

這是讀程式碼加規格後的靜態審查，沒有跑過、也沒做 exploit。每一條都附上證據位置（commit 已固定），等級是依照「如果照目前 repo 部署」來評。

H-1std PAL 把裝置根秘密寫死在原始碼裡，而 SEV-SNP sidecar 跑的就是這個 PAL
tessera-sw/fw/plat/std/pal/src/seed.rs:27（STD_MFGR_SEED_ROW0、STD_OWNER_SEED_ROW0、STD_FW_SEED48、STD_UDS）· CRD CRYPT-3、FW-SEC-4（禁止量產韌體含靜態金鑰或原始碼內秘密）· ddi_sock_server/src/main.rs:26 用的是 StdHsm

sidecar-scripts 提供了 mshv-unikraft-snp 這個 AMD SEV-SNP 版本，看起來像是「還沒有實體晶片前，先用機密 VM 當 HSM」。可是它裡面的 HSM 核心用的是 std PAL，而 std PAL 的裝置根秘密（UDS、FW seed、BKS1、BKS2）全都是 repo 裡的公開常數。註解寫明這些值取自「先前的參考韌體」，目的是讓 blob 和實機位元相容。

Tessera 的設計是讓分區金鑰同時依賴裝置內的秘密和外部提供的秘密，例如 PartInit 時由主機加密送入的 mach_seed，以及 Partition Owner 的 BKS3。裝置端秘密公開之後，這道雙重保護就只剩一半：掌握 mach_seed 的人可以在 HSM 外重算 UMS，以及由它推導的分區身分金鑰（PTA）；掌握 BKS3 的人也能在外部推導 Backup Key。換句話說，「金鑰只存在 HSM 邊界內」這個承諾在 sidecar 上不成立。SNP 擋得住 host 讀記憶體，擋不住「秘密本來就是公開的」。

在 std PAL 加一道 build-time 防線：production 設定下禁止使用寫死的種子，改成從 SNP 的 MSG_KEY_REQ（VCEK 推導的 sealing key）或 vTPM 取得 UDS。另外，要確認「實機 BKS1 和模擬器相同」只發生在開發用 SVN，正式 SVN 一定要有獨立的種子列。

H-2vsock DDI 傳輸完全沒有認證；如果 sidecar 被當成產品用，等於開放的 HSM
ddi_sock_server/src/main.rs:9 "This unauthenticated test transport is for trusted, isolated environments"

作者在註解裡寫得很清楚，這是測試用的傳輸層。但 sidecar repo 的 SNP 建置流程和產品化包裝（多種 variant、MSHV 平台、SNP 隔離）會讓人以為它是可以部署的東西。任何能連到 vsock CID:1234 的行程都能下 DDI 指令；唯一的門檻只剩 session PSK（見 M-1）。

sidecar 的 README 和建置腳本要明確標示 non-production。如果要產品化，至少要做到：SPDM-over-vsock 或 attested TLS（以 SNP report 作為身分），並把 SNP measurement 綁進 AOAC/FMC Alias 鏈。

M-1預設 PSK 是公開的，第一個連上的人就能拿走分區（TOFU 搶占）
Command Spec §Default-PSK gate · fw/core/lib/src/ddi/tbor/mod.rs:862 allowed_with_default_psk

預設 PSK 字串（TESSERAHSM-DEFAULT-CO-PSK-v1----）寫在規格裡。gate 的設計本身是對的：safe-by-default，新加的 opcode 會自動被擋，只開放 PskChange 和 SessionClose，而且有單元測試鎖住；新 PSK 也是用 session 金鑰加密傳送，每個 session 只能換一次。問題在於 bootstrap 是「先到先贏」：誰先送出 PskChange，誰就擁有 CO 角色。如果在合法 owner 輪替 PSK 之前，有其他能存取這個 VF 的行程先動手，就能搶下分區。

把第一次 PskChange 綁到 POTA 簽章（或綁到 TDISP 已鎖定的 TDI），讓 PSK 輪替本身也要有授權。或者至少在 PartInfo 裡回報「PSK 已被輪替」的時間點和計數，讓 owner 能偵測自己是不是晚了一步。

M-2RSA 引擎：CRT（效能路徑）和 exponent blinding 不能同時開，預設兩者都關；私鑰由 CPU 經匯流排寫入
tessera_rsa_ctrl.sv:265 · tessera_rsa_params_pkg.sv:79（CRT 與 BLIND_BITS 預設皆為 0）· tessera_rsa_top.sv:22 "No Key Vault interface… Private exponents arrive over the bus"

RSA 是 12 個 IP 裡唯一沒有 revinfo.yml 來源紀錄的區塊。檔頭註解自稱「Caliptra RSA engine」，但 CI 的 round-trip 沒有涵蓋它，所以無法證明它和任何經過審查的 upstream 版本一致。好消息是它有做：固定長度的 ladder、常數時間查表、強制的 Bellcore 驗證（防 CRT 故障注入）。壞消息有兩個：(1) 要達到 PERF-1 規格的 100k ops/s 就必須開 CRT，而 CRT 和 blinding 在 RTL 裡是互斥的；(2) 沒有 Key Vault 介面，私鑰由 CPU 寫進 RSA_D。這和 CRD 的 KEY-MGT-6（SHOULD：韌體不應看到明文金鑰），以及 Theory of Operation 裡「一般 uC 流程不得需要明文私鑰」的要求不一致。

讓 key mover 直接把 RSA 私鑰送進引擎（不經過 CPU），並擴大 DP/DQ 的寬度以支援 CRT blinding（dp + k·(p−1)）。在 tape-out 前要安排獨立的 SCA/FI 實驗室評估，例如 TVLA 和雷射故障注入。

M-3晶片真正的安全邊界還沒開源
tessera-rtl/src/ 只有 12 個加速器；CRD 要求的 key mover、pool manager、host memory hasher、GSRAM KV、PCIe IDE/TDISP、tamper 都還沒出現

加速器之所以安全，是因為「金鑰怎麼進來、誰能讀」，而這部分全在還沒公開的 SoC 整合層。換句話說，現在沒辦法驗證 Tessera 最核心的承諾：「解遮罩只在硬體狀態機內完成，uC 只能單向寫入」。另外，韌體 repo 裡唯一的實機平台是 Uno（Cortex-M，fw/plat/uno）；它和 CRD 規格中的 4×M7/E6 + PCIe Gen6 架構是不是同一顆晶片，repo 裡沒有說明。就連加速器本身也有缺口：ECC 引擎只看得到 P-384，CRD 要求的 P-256、P-256K、P-521 都還沒有硬體實作。

在 OCP 推動「SoC integration RTL + 安全架構文件」的公開時程；在那之前，任何商業材料都應該把 Tessera 定位成「參考架構」，不要說成「已驗證的晶片」。

M-4Linux 驅動：device reset 的 ioctl 沒有檢查權限，程式裡還留著 debug 記錄
tsra_hsm_dev.c:2146 TSRA_IOCTL_RESET_DEVICE · tsra_hsm_dev.c:2046 起共 4 處 "[REMOVE-ME]"

整個驅動裡沒有任何 capable() 檢查，所以能開 device node 的行程都能 reset 裝置。在 VM 裡面，這代表其他 user 可以讓 HSM 的服務中斷（DoS）；在 PF 端影響會更大。驅動有 23 處 copy_from_user，這次沒有逐一審查；FOLL_PIN 的使用者頁 DMA 路徑（tsra_dma_io.c）也值得找 kernel 專家再看一次。

reset 和管理類 ioctl 要求 CAP_SYS_ADMIN，並把 udev 規則加進 repo；拿掉 [REMOVE-ME] 記錄；送 upstream 前跑 syzkaller。

L-1規格和程式碼不同步，舊版 MBOR 協定仍然啟用

韌體已經實作並分派 ML-DSA 和 ML-KEM 的 6 個指令（0x26–0x2B），但 Command Spec v0.4 的 opcode 表只寫到 0x25，而 docs/tbor-ddi/commands/ 裡這 6 份文件仍寫著「Not implemented yet」。三份資料互相矛盾。MBOR 和 TBOR 兩套解析器並存，代表兩倍的解析攻擊面；24 個 fuzz target 都放在 fuzz/fuzz_targets/ddi/tbor/ 底下，MBOR 解析器有沒有被 fuzz 覆蓋，還需要再確認。

用 docs/tbor-ddi/commands/*.md 自動產生規格的 opcode 表；訂出 MBOR 的淘汰時程，並在 PartInfo 回報目前啟用了哪些協定。

L-2OpenSSL Provider 還沒有 PQC，也沒有 PKCS#11

Provider 目前只支援 RSA、EC、ECDH、AES-GCM/XTS、SHA-2、HKDF。可是韌體已經有 ML-DSA 和 ML-KEM，而 OpenSSL 3.5 原生就支援 ML-KEM/ML-DSA。另外整個專案沒有 PKCS#11 模組（native API 文件只列出各演算法對應的 PKCS#11 mechanism），而 PKCS#11 是傳統 HSM 生態（Java、資料庫 TDE、CA 軟體）的共通語言。

補上 provider 的 PQC keymgmt、signature、kem；PKCS#11 是一個明確的商業缺口（見 07）。

做得好的地方（之後寫產品材料可以引用）

OK Rust 預設禁止 unsafe

workspace 層級設定 unsafe_code = "deny"，需要 unsafe 的模組必須個別開啟。韌體核心可編成 no_std 的 async 函式庫，實機平台用 Embassy 執行。

OK Default-PSK gate 是白名單制

之後新增的 opcode 會自動被擋，有測試鎖住；PSK 輪替本身也以 session 金鑰加密，每個 session 只能換一次。

OK RTL 來源可追溯

CI 會把每個 vendored 區塊和 Caliptra upstream 的指定 commit 做 round-trip diff，證明改動「只有改名」。這是很少見的供應鏈紀律。

OK 回應帶 FIPS_APPROVED 旗標

每個回應都標示這次運算是否只用了 approved 演算法，對 FIPS 稽核很友善。

OK Fuzz 加上一致性測試

24 個 TBOR fuzz target、約 3,800 個 Rust 測試；C++ 一致性測試可以切換 mock、emu 或實機驅動後端。

OK 交易式 undo log

fw/core/undo 讓多步驟的狀態變更在中途失敗時可以回滾。

07用做生意的角度看 Tessera

本節的動機與市場影響是分析判斷，不是官方說法。先講結論：Tessera 是 hyperscaler 把「HSM」從一個設備生意，改寫成一個晶片標準和生態系生意。Caliptra 已經讓 Root of Trust 變成大家共用的公共財，Tessera 想對 HSM 做同一件事。

Microsoft 為什麼要開源？

  • 壓低自家成本：CRD 把 Tessera 定位為下一代 Azure Integrated HSM。開源加上多家供應商，可以讓晶片價格競爭，也避免被單一供應商綁住。
  • 讓自己的做法變成標準：透過 OCP 定義 DARC 和 Masking Key Transfer，讓 Azure 的金鑰模型成為業界預設，其他雲和 HSM 廠商就得跟著相容。
  • 搶監管紅利：DORA、主權雲、PQC 遷移時程都在逼企業證明「可以退出、金鑰從不外露」。開放標準是最有說服力的稽核證據。
  • Caliptra 的成功模式：參與者（Marvell、Oracle）願意一起署名，就代表供應鏈已經開始對齊。

誰的生意會被影響？

SWOT（從潛在參與者的角度）

S 優勢

  • hyperscaler 背書：CRD 定位為下一代 Azure Integrated HSM
  • 軟體堆疊完整，有模擬器，上手成本低
  • 全部開源（MIT、Apache-2.0、GPL-2.0），可以審查
  • 一開始就把 PQC 納入規格（ML-DSA、ML-KEM、hybrid）

W 弱點

  • 晶片安全邊界還沒開源，現在沒辦法驗證
  • 規格還是 v0.5，和程式碼不同步
  • 生態整合只有 OpenSSL
  • 版權和治理目前以 Microsoft 為主

O 機會

  • PQC 遷移截止時間（CNSA 2.0）帶來強制的換機潮
  • DORA 和主權雲對「可退出性」的需求
  • PKCS#11 和 KMS 整合還是空白市場
  • 台灣半導體供應鏈：ASIC 設計服務、封測、安全 IP

T 威脅

  • FIPS L3 的認證時程和成本
  • 規格可能被單一 hyperscaler 的需求帶著走
  • AWS、Google 推出自己的互斥方案
  • 開源之後，硬體毛利會被壓縮

給安全 IP 廠商（例如 PUF / RoT 供應商）的具體切入點

規格明文要求 PUF：CRD ROT-14（SHALL）要求 Tessera 內建 PUF，作為 Caliptra RoT 的裝置唯一熵與身分來源；ROT-15（SHALL）要求架構定義 PUF 衍生材料、fuse 材料或兩者如何進入 Caliptra 的身分推導與證明流程。這不是「可能的機會」，而是每一顆 Tessera 都必須滿足的需求，而且整合方式目前還沒定義。
Tessera 的需求規格依據現在的做法可以切入的產品
PUF 作為 Caliptra 的熵與身分來源CRD ROT-14、ROT-15規格要求但尚未定義整合方式；RTL 與韌體都沒有 PUFPUF IP，加上「PUF ↔ Caliptra 身分推導」的參考整合；可以主動提案寫進 ROT-15 的架構定義
UDS、BKS 等裝置根秘密的保存CRD ROT-5、Sealing Primitives §BKSstd PAL 寫死在程式碼；Uno 由 bks_store 驅動讀取PUF 推導或 PUF 加密保護的根秘密：免注入、抗探測，正好補上 H-1 的根因
SP 800-90B 熵源CRD §Random Numbers、SEC-PCIE-FEATURES-4RTL 只有 HMAC-DRBG（沒有熵源）通過 90B 驗證的 TRNG IP
防竄改：溫度、電壓、頻率監控、shieldCRD §Physical Security（FIPS L3 必要）RTL 裡還沒有Anti-tamper sensor IP 和防護層
Caliptra 2.2 subsystem 整合CRD ROT-1、ROT-2、ROT-12必須是 Caliptra 2.2，且不得有其他 RoT；整合需通過 OCP-SAFE 審查已經有「Caliptra + 自家 RoT」整合經驗的團隊，可以直接提供參考整合
RSA 和 PQC 加速器的 SCA 加固FIPS 140-3 L3 非侵入式攻擊緩解RSA 的 CRT 不能 blinding（M-2）經過 SCA 加固的 PKA IP，或提供 SCA 評估服務

以上「機會」是根據規格和程式碼缺口推出來的假設，還需要和 OCP 工作小組、潛在客戶驗證過才算數。這份文件刻意不放市場規模數字，因為沒有可靠的公開來源可以直接引用。
